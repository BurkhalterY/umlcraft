# UMLCraft mechanics sheet

UMLCraft is written in Rust with egui; the constants below appear under the same names in `src/`
(`views.rs` sizes, `render.rs` drawing and canvas, `ui.rs` window, `model.rs` file format, `app.rs` zoom).

Facts read from the original StarUML 7.1.1 (Electron 29) code in `resources/app.asar` (unpacked, readable JS) and
from a sample project the original saved itself (`checks/original/sample.mdj`, `sample2.mdj`).
Locations are `file:line` inside the unpacked asar, or a function address (`0x…`) in the native program
`/opt/StarUML/staruml`. Nothing here is pasted code; it is the rules, rewritten.

## Runtime (native program, decompiled)

`/opt/StarUML/staruml` (ELF x86-64, 176 MB) is the stock Electron 29.4.6 runtime (Chromium, V8, Node). The
decompiler finds no StarUML text in it: no `.mdj`, no `StarUML`, no menu or toolbox labels. Every modelling
rule below therefore comes from the JavaScript the runtime loads, which was read directly.

* Word wrap: a view with `wordWrap` on breaks its labels between words to the label width, and its minimum width is the widest single word plus padding (`src/core/core.js:3705-3727, 3769-3790`). UMLCraft applies this to the name and the attribute, operation and literal rows of class-like boxes; notes and text wrap only while their `wordWrap` is on (default on).

* Robustness: a class stereotyped «boundary», «entity» or «control» with Stereotype Display Icon (or Icon with Label) is drawn as the UML robustness icon with its name below; the Robustness tools create such a class with attributes and operations suppressed (`extensions/default/robustness/main.js:17`). UMLCraft draws its own icons in a 50×36 area (estimated).

* Ball and socket: a dependency on an interface shown as a ball (icon display) is drawn as a solid line ending in a half circle around the ball, 5 px outside it, open towards the ball (UMLCraft's estimate of the documented socket notation, docs.staruml.io class-diagram).

* Component and deployment diagrams (UMLCraft's estimates of the standard UML shapes): a component is a box with the component icon (14×16 with two 8×4 tabs) at its top right; an artifact is a box with a page icon, or in icon display (the default, `uml.artifact.stereotypeDisplay`) a 30×40 page with the name under it; a node is a box with a 10 px depth above and to the right; a deployment is a dashed arrow labelled «deploy»; a communication path is drawn and edited like an association. Components and nodes start with attributes and operations suppressed (`extensions/essential/uml/preferences/uml.json`).

* Ownership dot: an association end with an `ownerAttribute` gets a filled dot of radius 3, 6 px from its tip along the line (UML 2.5 notation; size and place estimated).

## Element Picker and type names

* A name typed into a `type` or `stereotype` property is looked up among elements of the field's type (UMLClassifier or UMLStereotype): first the owner's namespace, then each enclosing namespace, then the whole project; a match is stored as a reference, otherwise the text (`views/property-editor-view.js:604-622`, `core/repository.js:2353-2361`).
* The Element Picker ("Select Element") opens with the current value selected and its owners expanded, or "Do not specify" checked; a choice of the wrong type gives "Selected element (X) is not an instance of T" (`dialogs/element-picker-dialog.js:289-346`).

## Mermaid import

* Class diagrams: the container is a new "Package by Mermaid" unless a package is the base; the diagram is "Class Diagram by Mermaid". Members are `Type name`; visibility `+ # - ~`, none is package. `<|--` generalization, `..|>` realization, `()--` lollipop realization, `o` shared, `*` composite, `<`/`>` navigable, other dashed links dependencies. Layout uses `direction` (default TB) with separations 50 (`extensions/default/mermaid/factory/class-factory.js:40-540`, `utils.js:1-21`).
* Bases (`mermaid:generate-diagram(code, base?)`): no base means the project. Class and ER need a UMLPackage ("Base element must be a UMLPackage"), sequence and state a package, classifier or operation ("Base element must be a package, classifer or operation", sic), flowchart and mind map any model element. The dialog itself passes no base; UMLCraft passes the element focused in the explorer when it fits (`main.js:135-185`, each factory's "prepare base model").
* Sequence diagrams: "Collaboration by Mermaid" in the base holds "Interaction by Mermaid", which holds "Sequence Diagram by Mermaid". `showActivation` is on only when the code activates something (`activate`, `deactivate`, `+`/`-`), `showSequenceNumber` only when `autonumber` appears (even `autonumber off`). Each participant, in order of first appearance, is a role `<name>Role` (a UMLAttribute of the collaboration) and a lifeline named by its alias; `actor` adds a UMLActor typed onto the role and shows the lifeline as an icon. Lifeline views start at x = 25, top 40, 70 wide, 150 px apart; their height is the span of their messages + 60, at least 120. Messages start at y = 110, 60 px apart; a fragment start adds 30 first, and the fragment's top is 55 above that row, its bottom 20 under the row after its last message. Each message sets the innermost open fragment's left to 15 px left of the leftmost of its two lifeline centres and widens it to cover both (+30). Each operand view is 60 high. Notes are 40 high on the current row (then +60): over spans the lifeline centres ±15, left of / right of is 100 wide, 15 px from the centre. Sorts: the message right after `create` is a createMessage, the one right after `destroy` a deleteMessage when it goes to the destroyed participant; `-->>` asynchSignal, `-)` asynchCall, `--)` reply, everything else synchCall. A message without text is named by its index in Mermaid's message list. `rect`, `box`, links and properties make nothing; `par_over` makes nothing either, and its `end` then closes the enclosing fragment in the original, which UMLCraft does not copy (`factory/sequence-factory.js:48-430`, `parser/sequence/sequenceDb.js`, `sequenceDiagram.jison`).

## XMI export

File › Export › XMI Export (v2.1) writes OMG XMI 2.1 (`xmlns:uml="http://schema.omg.org/spec/UML/2.1"`), model elements only. The layout is UMLCraft's own, as StarUML's XMI extension was not read: packages hold `packagedElement`s; a classifier holds `ownedAttribute`, `ownedOperation` (with `ownedParameter`), `ownedLiteral`, `generalization` (`general`) and `interfaceRealization` (`client`, `supplier`, `contract`); associations, dependencies and other relationships go in the nearest package, an association with its two `ownedEnd`s; use cases hold `include` (`addition`) and `extend` (`extendedCase`); multiplicities become `lowerValue`/`upperValue`; documentation becomes an `ownedComment`. Types given as text are left out.

File › Import › XMI Import (v2.1) puts what it reads into a new UMLModel `XMIImported` under the project (https://docs.staruml.io/user-guide/managing-project/). Members without `xmi:type` are known by their tag; a property with an `association` is an association end, not an attribute; a type given by `href` (a primitive library) becomes a text type named after the part after `#`.

## HTTP API

* A local server (127.0.0.1, port 58321) starts with the window, not for command-line commands; `settings.json` keys `apiServer` and `apiServerPort` turn it off or move it. `GET /` greets; `POST /generate_diagram {code}`, `/get_all_diagrams_info`, `/get_current_diagram_info` (records `{id, type, name, description}`) and `/get_diagram_image_by_id {diagramId}` (unknown id: 500 "Diagram not found or invalid ID") (`src/main-process/api-server.js:12-154`, `main.js:33-38`). UMLCraft's image answer is `{success, data, mimeType}` (estimated) and its greeting names UMLCraft.

## Keymap

* `keymap.json` in the settings folder maps keystroke descriptors (`cmdctrl-alt-g`: modifiers then the key, case-insensitive, `cmdctrl` = Cmd on macOS and Ctrl elsewhere) to command ids; the user's bindings override the defaults for the same keystroke, and a bad file is logged and ignored (`ui/keymap-manager.js:49-54, 154-292`, `app-context.js:760-764`). UMLCraft's settings folder is `UMLCraft` instead of `StarUML`, and its command ids are the ones the Command Palette lists.

## Snapping

* While a moved or resized coordinate stays in the grid cell it started in, it keeps its original value; once it crosses into another cell it snaps to the nearest grid multiple (`src/ui/diagram-editor.js:1201-1323`). UMLCraft applies this to box moves and resizes, not to bend points.

* Statecharts: a state is a rounded box (radius 10) with its name and, under a line, one `entry/ name`, `do/ name` or `exit/ name` row per activity (that layout is estimated). Pseudostates and final states are made unnamed, at their smallest size wherever the tool is released, and are freely sizable from there: initial a filled circle of 20 px, choice a 23 × 19 diamond, junction a filled 15 px circle, shallow and deep history 26 px circles with H or H*, entry and exit points 15 px circles (the exit point with an X), terminate a 26 px X, fork and join filled bars 6 thick and at least 70 long (horizontal unless taller than wide); a final state is a circle of at least 26 px around a filled one. A pseudostate view is a floating node whose labels are hidden; a final state view a plain node. A submachine state shows `name: Machine`, keeps 16 px for the submachine mark (two small circles joined by a line) at its bottom right. A connection point reference goes in its state's `connections`: a 14 px circle centred on the state's border, with an X when it refers to exit points, labelled with the names of its `entry` and `exit` points. Add Join puts a join 40 px above the state and two states 80 px above the join. A transition is a solid line with an open arrow labelled `trigger1, trigger2 [guard] / effect`, owned by its source's region (`extensions/essential/uml/elements.js:120-152, 8835-9230, 9502-9600`; `extensions/essential/uml/grammars/uml-transition.pegjs`; `uml-factory.js:2005, 2116-2214`; `uml-commands.js:2947-2963, 3314-3378`).
* Activities: an activity diagram lives in an activity (a new "Activity1"… when added elsewhere); its nodes go in the activity's `nodes` and its flows in `edges`. An action is at least 60 × 40 with corners rounded by 10 (15 px wider when it calls a behaviour); Send Signal is a pentagon whose point is a quarter of the height deep, Accept Signal a box notched by the same depth, Accept Time Event a 24 px hourglass above the name. Control nodes have no name compartment: initial 20 px, activity and flow final 26 px, decision and merge diamonds 23 × 19, fork and join bars 6 thick and at least 70 long, horizontal unless taller than wide. Object nodes are plain boxes with `name: Type`, and «centralBuffer» or «datastore» for those kinds. A flow's label is `name [guard] {weight=w}`. A swimlane is a partition in the activity's `groups`: at least 50 × 300 (vertical) or 300 × 50 (horizontal), its name 4 px into a filled header; activity nodes put in a lane move into its partition's `nodes` and back to the activity's when taken out (`elements.js:179-187`, `uml/main.js:24-41`, `engine.js:1158-1166`). Pins are 18 px squares kept just outside their action, with an arrow into the action (input) or out of it (output); an object flow drawn between two actions joins a new output pin to a new input pin (`elements.js:159-160, 9662-9840`; `uml-factory.js:2313-2370`). An interruptible region is a group (`groups`), a dashed unfilled rounded box at least 30 × 30; a structured activity (and an expansion region, mode `iterative` by default) is a node, a filled box with a dashed rounded border, «structured» (or «iterative», «parallel», «stream») left-aligned over its name; the activity nodes put in either move into its `nodes`. Expansion nodes are unnamed `UMLExpansionNode`s in an action's `inputs` or `outputs`, four 18 px cells long along the border they sit on. An exception handler joins two actions: it ends on a new input pin of the handler action (its `target`), and its `handlerBody` is that action; it and an activity interrupt carry a `UMLZigZagAdornmentView` 25 × 20, 20 px off the middle of the line at α = π/2. An activity edge connector is a node named "A", a 26 px circle with its name inside. * Sequence diagrams: a sequence diagram lives in an interaction (a new "Interaction1" in a classifier, else in a new collaboration "Collaboration1") and starts with a 692 × 592 frame of itself at (8, 8). Replies and create messages are dotted; calls and deletes end in a filled arrow, the others an open one; create and delete messages show «create» and «destroy», a delete message crosses out the end of its lifeline. * Communication diagrams: a communication diagram is wrapped like a sequence diagram (an interaction, in a collaboration's new "Interaction1", else in a new collaboration) and starts with the same frame.
